### Tech-leader

**You own the proposal and plan, not the production implementation.** Use for `tech-leader` or a request to compare approaches and plan a specific feature. A request to implement goes to Feature. A program-level or stacked-PR planning request goes to Multi-phase plan. Do not let the general large-work fallback turn this planning request into an execution run.

## Scope and handoff

Invoke through `/tech-leader <feature>` using the [entry skill](../../tech-leader/SKILL.md), or through `/gt36-mode tech-leader <feature>`. Both entries run this playbook; keep the sequence and document contract here, not in the entry skill.

The only repository output is `docs/designs/<feature-slug>.md` in the target project. Use the same document for the architecture and implementation plan, and update it on revisions without overwriting an unrelated design. No application source, tests, snapshots, fixtures, configuration, or production skeletons may be changed. Do not call applier, create commits, push, open PRs, merge, or schedule execution. A broad autonomy grant does not change this scope.

Necessary probes or competing prototypes may run only in isolated temporary directories outside application source. Do not edit the target to make a probe work, create a production integration, or update its test artifacts. Capture observations and limitations, clean up processes you started, and distinguish source-traced behavior, observed probe results, and untested hypotheses. Put the useful results and commands in the document so temporary files are not required to understand the decision.

Read **principle-exhaust-the-design-space** and **principle-laziness-protocol** in full. Apply the former during architect's design exploration and the latter when comparing, synthesizing, and sequencing. They are criteria throughout, not extra investigation stages. Prefer reuse and the smallest architecture that meets the actual feature requirements.

## Steps

1. **Recall relevant context.** Use **recall** for prior decisions and work on the feature. Pass context already supplied by the human instead of mining it again. If there is no accessible relevant history, or the human already supplied a complete capsule, keep this step as `skip: <reason>` and continue from the available evidence. Do not invent historical decisions or read unrelated workspaces.
2. **Sharpen the feature brief.** Use **sharpen** on the original request plus recalled context. Record the goal, affected users, in/out of scope, constraints, observable acceptance criteria, and unresolved product decisions. Improve the request without growing it. Ask the human about blocking product choices that evidence cannot settle; do not choose silently. Resolve facts by reading or narrowly scoped temporary probes.
3. **Ground and design with architect.** Pass the brief and existing findings to **architect**. It uses **explainer** for current mechanics and **investigator** when historical rationale matters, reusing prior findings but checking key facts. Require actual analogous feature/function files and symbols, existing module/import/helper conventions, and candidate API contract exports and consumers. Investigator's NEEDS_CONTEXT goes to this coordinator for one batched provide/skip question; wait for an answer or explicit skip, never infer it from silence. Mark missing or partial context and code/context contradictions honestly.
4. **Compare through architect's arena.** This is architect's nested **arena** phase, not a second independent invocation. Require at least two structurally distinct candidates, use the existing architect runners configuration, and screen with architect's design red flags. Compare correctness, fit with project precedents, caller experience, interface/ownership boundaries, API contract fit, implementation complexity, and verification feasibility. Show accepted tradeoffs and rejected alternatives. Run temporary prototypes only when they answer a concrete unknown. Retain uncertainty where evidence does not discriminate. Save the chosen architecture in the shared design document with its revision and pending approval.
5. **Build the implementation plan with figure-it-out in plan-only mode.** Give **figure-it-out** the brief, code findings, alternatives, proposed architecture, risks, and the same document path. This is read-only planning after architect, not implementation and not architectural approval. Reuse the selected architecture without another arena or architect run. Split the work into ordered, independently understandable units with dependencies, intended file/module scope, behavior to deliver, acceptance criteria, and how existing checks or real-surface observations will verify it. Identify independent versus shared-state work, rollout/compatibility or migration needs where relevant, and unresolved decisions. Propose test changes only as specifically named edits awaiting explicit human authorization. Do not build a harness or execute the units. If planning exposes a material design gap, record it for revision rather than silently changing the architecture or relaunching design exploration.
6. **Teach from supplied findings.** Use **teach** in supplied-findings mode with the brief, design, evidence, comparison, and plan. Explain what the feature will do, the recommended approach, why it fits this project, its tradeoffs, and the implementation order. Do not rerun explainer/investigator by default or start another context interview. A specific unresolved gap can receive a narrow read-only follow-up under the same scope. Keep inference labels and unresolved risks. Use inline diagrams where helpful; do not add extra repository artifacts.
7. **Hand back and stop.** Review the document for consistency and missing evidence. Return its path, the recommendation, important tradeoffs, and the decisions requiring human approval. End as **Awaiting design and plan approval**; if blocking questions remain, identify the draft as not ready for execution. Do not run Opening a PR. Providing context or approving a direction during planning is not permission to start production work. A later explicit implementation request must pass the current architecture revision and human approval to applier.

## Document contract

Write every document created or revised during this workflow in English, regardless of the language of the user's request. Apply this to briefs, architecture proposals, implementation plans, headings, tables, and diagram labels, and pass the requirement to every delegated or nested skill. Preserve exact code identifiers, file paths, and verbatim source quotations. Conversation with the user may remain in the user's language.

Keep one document using architect's rationale structure, extending it with the feature brief and evidence rather than replacing the architecture sections with an unrelated plan template. Include:

- **Feature brief and scope.** Goal, affected users, constraints, acceptance criteria, and exclusions.
- **Project evidence.** Real analogous features/functions with paths and symbols, established conventions, recalled decisions, current mechanism, and relevant Git/ticket context with its provenance and confidence.
- **API contracts.** The contracts/exports inspected and their request/response and business fit, or a concrete gap and proposed resolution. Do not invent an export. Mark an unaccepted fallback as pending; generic plan approval does not accept a missing-contract resolution unless that proposal was explicitly presented and accepted. Record not applicable for work without an API boundary.
- **Usage and architecture.** Caller examples first, type/API sketches in fenced blocks, module ownership, data flow, and invariants.
- **Alternatives and synthesis.** At least two structural candidates, comparison, chosen base, relevant grafts, rejections, accepted tradeoffs, probe evidence, and limits.
- **Implementation sequence.** Ordered units with dependencies, intended scope, outcomes, and verification. No claim that a proposed unit was implemented or verified.
- **Verification and test permissions.** Existing commands/surfaces, observable pass criteria, known limitations, and separately named proposed test edits requiring explicit human authorization. Do not add tests simply to make the plan look complete.
- **Risks and open decisions.** Missing facts, product choices, contract exceptions, compatibility/rollout concerns where applicable, and the evidence needed to resolve them.
- **Revision and review status.** Identify the version being presented and what changed on revision. End pending explicit human approval; never self-approve or imply that a parent/worker verdict is human approval.

The plan may be assembled and explained while architecture approval is pending because it does not execute the architecture. The architecture gate still applies before production implementation. Approval of a plan with clearly identified test edits can authorize those edits only when the human explicitly approves them. Do not infer that authorization from a generic "looks good" about the overall approach.

**Reply:** the document path, a plain explanation of the feature and proposal, the comparison and tradeoffs, the implementation sequence, limits, and decisions waiting on the human. No implementation or PR link to invent.
